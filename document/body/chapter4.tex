\chapter{Distributed Resource Utility \&{} Performance Testbed} \label{chap:ch4}

To answer the research questions outlined in Chapter \ref{chap:intro}, 
we developed the \ac{DisRUPT}
that can evaluate the performance of distributed resource management algorithms. 
In this chapter, we will discuss the design and implementation of \ac{DisRUPT} using 
Raspberry Pi\footnote{https://www.raspberrypi.com/} devices along with a set of 
\acp{MCU}. The Raspberry Pi devices serve as our reference for edge devices, as
they are more computationally capable than the \acp{MCU}, while keeping a low power
consumption, opposed to laptop computers, that could also be used as edge devices. 

This testbed will allow us to easily partition a model, deploy it and test various use 
cases, in such way that we can evaluate the inference latency and the network's energy 
consumption under different partitioning and deployment strategies.

\section {System Overview} \label{sec:se41}

The \ac{DisRUPT} framework consists of four main components. Two inference interfaces: 
the Raspberry Pi Interface and the Microcontroller Interface. These
mentioned components are automatically managed and the network performance 
is evaluated by the Orchestrator Module. 
A Partitioning Module is also included, which is responsible for partitioning the models, 
before the deployment stage, and it is not involved in the inference process itself.

To achieve the collaborative inference, we first use the Partitioning Module to 
partition the \ac{DNN} models into all possible partitions that might be executed on 
the constrained devices. Then, the
segments and devices that will execute them are selected according to the devices
capabilities and the model requirements. Finally, the segments are deployed to the
respective devices, that are also configured to communicate with each other effectively.

Each device in the network runs its corresponding interface, which is responsible for
the execution of the assigned inference subtasks. Furthermore, it allows 
communication with other devices in the network, providing mechanisms to receive input 
data and transmit the results of the subtask.

In order to automate the deployment of the task to the network, we developed a set of
scripts that not only create routes that chain together the inference pipeline, but also
upload the partitioned submodels to the devices and feed the network with the input data.
This results in the Orchestrator Module, that is given the network configuration and
input data by the developer, through a configuration file. The Orchestrator Module
is also capable of collecting the performance metrics during the inference process,
for later analysis and comparison.

\section {Model Partitioning} \label{sec:se42}

Before the network configuration phase, we need to partition the \ac{DNN} models into
segments that are fit for the constrained devices in our network. To achieve this, we
will use the \ac{NAMP}'s model surgery module, that allows us to easily partition and
optimize \acp{MLP} and \acp{CNN} into said segments.~\cite{rego::namp}

\ac{NAMP}'s Partitioning Module takes a \ac{DNN} as input and generates a set of all 
possible model partitions by breaking it down layer by layer. Additionally, certain 
\ac{FC} layers can be partitioned to allow wide layers to be executed collaboratively 
across multiple devices. This module also enables model quantization to optimize the 
resulting segments, reducing their memory footprint for deployment on 
resource-constrained devices.

To achieve this, the weights and activations of the submodels are quantized from 
32-bit to 8-bit representations using TensorFlow's post-training quantization tools. 
First, the module generates all possible submodels in the standard TensorFlow format 
for every combination of beginning and ending layers. If flagged for optimization, 
each submodel is then quantized to 8 bits and ultimately converted into the $.tflite$ 
format.


\section {MCU Interface} \label{sec:se43}

To enable the execution of inference tasks on \acp{MCU}, we utilized 
embServe\cite{embserve_oliveira_2023},
a runtime application built on top of the Zephyr RTOS~\footnote{https://www.zephyrproject.org/}, 
which enables the deployment and execute services on constrained devices. 
This choice was motivated by our State of the Art analysis, as it fills the gap by 
supporting model deployment on far-edge devices with minimal overhead.

This framework provides an agnostic interface to the underlying hardware, allowing us to
easily deploy the partitioned submodels to the \acp{MCU} as services, and also to manage
the communication routes between the devices in the network.

To deploy the partitioned submodels, we need to compile an embServe service: a C
application that dictates the behavior of the device when that service is active,
in this case, the inference execution upon receiving input data. The service is then
uploaded to the device, and after defining the incoming and outgoing communication 
routes, the device is ready to partake in the inference network.

To facilitate the interaction with the Raspberry Pi and to enable the deployment
of inference tasks, we have developed a custom API that allows us to manage the
Raspberry Pi's resources and execute inference tasks remotely, while also transmitting
the intermediate results to the next device in the pipeline, monitoring the system
along the way.

This was achieved by creating a Python runtime application on the Raspberry Pi. The
application creates a server that listens for incoming requests to allow the Raspberry
Pi to partake in the inference network, from reporting its status, having configurable
outgoing communication routes, and executing the assigned inference tasks. It should
be noted that the Python language does not hinder the performance of the inference tasks,
as the used TFLite runtime is implemented in C, limiting the Python overhead to the
communication parsing and the server management.

The server creates a set of objects, as described in Table~\ref{tab:RPi-components}, 
that interact with each other to allow for the integration of the device into the

\section{Deployment Planning}\label{sec:se45}

To reduce the impact of constrained devices' limitations on the performance of the
distributed inference, we need to carefully plan the deployment and the communication
between the devices during the inference process. This involves selecting the most
suitable partitioning and deployment strategies, as well as optimizing the 
communication protocols to minimize latency and energy consumption. 

In this section, we will discuss the strategies and techniques that can be employed
to achieve the aforementioned goals, and how they can be implemented in the 
\ac{DisRUPT} framework.

\subsection{Device Communication}\label{sec:se451}

% CoAP protocol usage
% Minimized data per transmission
% Communication only in setup stages and between segments 

Besides each device being responsible for its assigned inference subtask, they also
need to communicate with each other to bring meaning to the inference process, which 
takes a toll on the network performance.
In order to ease the communication overhead between the devices, we have taken several
measures such as the messaging protocol selection, the minimization of the data
transmitted, and the reduction of the communication stages during the inference process.

The CoAP web transfer protocol~\cite{coap-rfc7252} was selected for the communication
between the devices, as it is a lightweight protocol, as presented in the 
Figure~\ref{fig:coap-arch}, designed for constrained devices
and networks, making it well-suited for our use case. Specifically, CoAP operates over
UDP rather than TCP, drastically reducing connection handshake overhead, transmission
delays, and power consumption. To fit low-power payload limits, it uses a compact
4-byte binary header that reduces fragmentation. Its dual-layer design adds reliability
via confirmable messages while preserving REST semantics (GET, POST, PUT, DELETE).

% Specifically, CoAP operates over 
% UDP rather than TCP, drastically reducing connection handshake overhead, transmission 
% delays, and power consumption. To adapt to the strict payload limitations of low-power 
% wireless networks and minimize packet fragmentation, it replaces verbose, text-based 
% HTTP headers with a highly compact 4-byte fixed binary header. Furthermore, CoAP 
% introduces a dual-layer architecture that separates the messaging layer (handling 
% reliability through confirmable messages) from the request/response layer. This allows 
% it to preserve standard RESTful semantics (GET, POST, PUT, DELETE) for easy 
% interoperability with existing web infrastructure, while augmenting communication with 
% native IoT optimizations. These include built-in resource discovery via 
% /.well-known/core, IP multicast support, and an asynchronous Observe mechanism that 
% enables push-based data streaming without the energy waste of continuous client polling.

To further minimize the communication overhead during inference, we have separated the
communication into two main stages: the setup stage and the inference stage. During the
setup stage, we transmit all the necessary information to allow the device to perform
the inference task and to communicate with the other devices in the network, such as
the routes used to manifest the inference pipeline, as well as the services containing
the inference model logic. 
On the other hand, during the inference stage, we restrain the communication to only 
the necessary information for the inference process, which is the intermediate results
between the segments. For inter-device communication, we encode payloads in
\ac{CBOR}~\cite{cbor-rfc8949}, a compact binary serialization format.
Compared with text-based \ac{JSON}, \ac{CBOR} reduces message size and
parsing cost. We use \ac{JSON} for setup and debugging (when messages are
inspected by tools or developers), but avoid it during production inference.

One of the goals of this work is to evaluate the performance of the inference
network under different partitioning and deployment strategies. With \ac{DisRUPT} 
performance can be measured through the inference latency and the network energy
consumption, which are crucial indicators of the inference process efficiency and 
effectiveness.

The Orchestrator Module is responsible for collecting these performance metrics during
the inference process. In particular, the inference latency is measured by recording
the timestamp of a given inference task and matching it with the timestamp of the final
result using a unique identifier assigned to each distributed inference task. 

The energy consumption of the network is measured using an external power profiler 
connected to the devices, allowing us to monitor the energy usage during the inference 
process and reporting it to the Orchestrator Module, as
to not interfere with the devices' performance. This data is stored for further 
analysis and comparison between different strategies.

All this data allows us to estimate the performance of the inference network under
different configurations, and to identify the most effective strategies for deploying
\ac{DNN} models on constrained devices. This data can also be used to develop several 
heuristics for future deployments, allowing us to match the user's needs with the most
suitable partitioning and deployment strategies, to achieve minimal latency, energy
consumption, or a balance between the two. 


\subsection{Partition and Deployment Strategies}\label{sec:se453}

% Where to partition the model
% Which devices to select for the execution of each segment

Another important aspect of the deployment planning is the selection of the
partitioning and deployment strategies. The way we partition the model and
assign the segments to the devices can have a significant impact on the performance
of the inference network.

% To further minimize the communication load and therefore the latency in the inference
% task, we can choose to partition the \ac{DNN} in such way that the partition points 
% are the layers that produce the smallest intermediate results. This way, directly
% reducing the amount of data that needs to be transmitted between the devices.

When it comes to the deployment strategy, the most relevant aspect to consider is the
\ac{DNN} architecture, as some layers are more computationally intensive than others.
Even if the layers in \ac{CNN} models and \ac{MLP} models are based on a series of 
matrix multiplications, the variations in the dimensions of the matrices and the
number of parameters can lead to significant differences in the computational load of
each layer.

In order to achieve the best performance, we need to carefully select the devices
that are more appropriate for the execution of each segment, considering their
computational capabilities and the memory constraints. 

Nonetheless, the relationship between the layers' computational load and the devices' 
capabilities is not always straightforward, so for this work, we will create several
scenarios with different deployment strategies, to evaluate their performance and to
identify the most effective ones for different use cases and requirements, as presented
in Table~\ref{tab:deployment-strategies}, while always considering the constraints
of the devices in the network.
